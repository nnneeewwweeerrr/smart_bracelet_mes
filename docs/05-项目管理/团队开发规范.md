## 一、Git 分支管理规范

### 1.1 分支结构

```
master (主分支 / 受保护)
  └── dev (开发分支 / 集成分支)
        ├── feature/order        (订单模块)
        ├── feature/purchase     (采购模块)
        ├── feature/stock        (仓储模块)
        ├── feature/production   (生产模块)
        ├── feature/quality      (质检模块)
        ├── feature/equipment    (设备模块)
        ├── feature/system       (系统管理)
        ├── feature/web-admin    (管理端)
        ├── feature/mini-app     (小程序端)
        ├── fix/bug-xxx          (问题修复)
        └── hotfix/urgent-xxx    (紧急修复)
```

### 1.2 分支规则

| 分支 | 用途 | 权限 |
|------|------|------|
| `master` | 生产发布版本，**禁止直接推送** | 仅项目负责人 |
| `dev` | 日常开发集成分支 | 全部成员可推送 |
| `feature/*` | 个人功能开发分支 | 开发者本人 |
| `fix/*` | bug修复分支 | 开发者本人 |
| `hotfix/*` | 线上紧急修复 | 项目负责人审核 |

### 1.3 流程

1. **首次拉取**：从 `master` 拉取 `dev` 分支到本地
   ```bash
   git clone https://gitee.com/guajila0627/smart_bracelet_mes.git
   cd smart_bracelet_mes
   git checkout -b dev origin/dev
   ```

2. **开发前**：从最新 `dev` 拉取自己的功能分支
   ```bash
   git checkout dev
   git pull origin dev
   git checkout -b feature/order
   ```

3. **开发完成**：推送到远端功能分支
   ```bash
   git add .
   git commit -m "feat: 完成订单管理CRUD接口"
   git push origin feature/order
   ```

4. **合并到 dev**：在 Gitee 上提交 Pull Request，由负责人审核合并

5. **禁止事项**：
   - ❌ 禁止直接向 `master` 提交代码
   - ❌ 禁止把 `dev` 分支的提交 `merge` 到自己的功能分支（会引入交叉依赖）
   - ❌ 禁止提交 `.idea/`、`target/`、`node_modules/`、`dist/` 等目录

## 二、提交信息规范（Commit Message）

### 2.1 格式

```
<type>: <subject>

<body>（可选）

<footer>（可选）
```

### 2.2 Type 类型

| Type | 说明 | 示例 |
|------|------|------|
| `feat` | 新功能 | `feat: 订单管理新增导出Excel` |
| `fix` | 修复bug | `fix: 修复生产报工数量校验错误` |
| `docs` | 文档变更 | `docs: 更新部署手册` |
| `style` | 代码格式（不影响功能） | `style: 统一缩进为4空格` |
| `refactor` | 重构 | `refactor: 抽取通用返回结果类` |
| `test` | 测试相关 | `test: 补充订单模块单元测试` |
| `chore` | 构建/工具/依赖 | `chore: 升级SpringBoot到2.7.18` |
| `perf` | 性能优化 | `perf: 优化库存查询SQL` |

### 2.3 Subject 规范

- 使用中文或英文均可，但**项目内必须统一**
- 不超过 50 个字符
- 动词开头，第一人称现在时
- 不加句末标点

### 2.4 示例

```bash
git commit -m "feat: 订单模块新增批量导入功能"
git commit -m "fix: 修复仓储入库扫码重复提交问题"
git commit -m "docs: 完善接口设计说明书"
```

## 三、命名约定

### 3.1 后端命名（Java）

#### 包名
统一根包：`com.mes`
模块包结构：
```
com.mes
├── controller     # 控制层
├── service        # 业务接口
│   └── impl       # 业务实现
├── mapper         # 数据访问
├── entity         # 实体类
├── dto            # 入参对象
├── vo             # 出参对象
├── config         # 配置类
├── common         # 通用类
├── utils          # 工具类
└── exception      # 异常类
```

#### 类名
- Controller：`XxxController`（如 `OrderController`）
- Service 接口：`XxxService`
- Service 实现：`XxxServiceImpl`
- Mapper：`XxxMapper`
- Entity：`Xxx`（如 `Order`、`OrderItem`）或 `XxxEntity`
- DTO：`XxxDTO` / `XxxReq` / `XxxQuery`
- VO：`XxxVO` / `XxxResp`
- 配置类：`XxxConfig`
- 工具类：`XxxUtil` / `XxxUtils`

#### 方法名
- 查询：`getXxx`、`findXxx`、`listXxx`、`pageXxx`、`countXxx`
- 新增：`addXxx`、`saveXxx`、`insertXxx`
- 修改：`updateXxx`、`modifyXxx`
- 删除：`deleteXxx`、`removeXxx`
- 导入导出：`importXxx`、`exportXxx`
- 业务方法：`动词+业务名`，如 `submitOrder`、`approvePurchase`

#### 变量名
- 使用小驼峰：`orderNo`、`userId`、`createTime`
- 常量：全大写+下划线：`MAX_PAGE_SIZE`、`DEFAULT_STATUS`

### 3.2 前端命名（Vue3 / uni-app）

#### 目录与文件
- views 下按业务模块建子目录，目录名小写：`order/`、`purchase/`
- 页面文件：首字母大写驼峰 + `.vue`：`OrderList.vue`、`OrderDetail.vue`
- 组件：PascalCase：`TableCard.vue`、`StatusTag.vue`
- API 文件：模块+Api 后缀：`orderApi.js`、`userApi.js`
- 工具方法：`xxxUtil.js` / `xxxUtils.js`

#### 接口请求路径
统一前缀 `/api`，后端Controller统一使用 `@RequestMapping("/api/xxx")`：

```
/api/order/list
/api/order/save
/api/order/update
/api/order/delete/{id}
/api/order/detail/{id}
/api/order/export
/api/order/import
```

#### 变量与方法
- 变量：小驼峰 `orderList`、`userName`
- 方法：小驼峰动词开头 `getOrderList()`、`handleSubmit()`
- 常量：全大写下划线 `MAX_PAGE_SIZE`
- 组件props：小驼峰 `orderData`、`showModal`

### 3.3 数据库命名

- 表名：小写+下划线，复数形式（部分单数），如 `sys_user`、`order_customer`、`purchase_order`
- 字段名：小写+下划线：`user_name`、`create_time`、`is_deleted`
- 主键：`id`（统一bigint自增）
- 逻辑删除字段：`is_deleted`（0-未删，1-已删）
- 创建/更新字段统一：`create_by`、`create_time`、`update_by`、`update_time`

## 四、代码风格

### 4.1 后端
- Java 代码使用 4 空格缩进
- 类、方法必须有 Javadoc 注释
- 启用 Lombok，简化 getter/setter
- MyBatis XML 文件按模块分包：`resources/mapper/xxx/`
- 统一使用 `Result<T>` 包装返回结果
- 异常统一由 `@RestControllerAdvice` 全局处理

### 4.2 前端
- Vue 文件使用 2 空格缩进
- 组件 `<template>`、`<script>`、`<style>` 顺序固定
- 使用 Composition API + `<script setup>`
- Element Plus 组件 PascalCase 引用
- API 调用统一封装在 `src/api/` 下，按模块拆分
- 全局状态使用 Pinia

## 五、Code Review 规范

- 所有合并到 `dev` 的代码必须经过至少 1 人 Review
- Review 检查项：
  - 命名是否符合规范
  - 是否有明显 bug
  - 是否有性能问题
  - 是否有安全风险（SQL注入、XSS、权限绕过）
  - 是否影响其他模块
